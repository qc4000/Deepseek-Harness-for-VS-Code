# SDD：规格驱动开发流程

> 本仓库自 1.0.0 起采用 **SDD（Spec-Driven Development）+ TDD**：先写清「做什么、为什么、怎么验收」，
> 再写「怎么做」，再拆「几步做」，每一小步先红后绿。
> 上位约束见 [../CONSTITUTION.md](../CONSTITUTION.md)；测试细节见 [../TESTING.md](../TESTING.md)。

## 1. 为什么这个项目需要 SDD

- **契约来自外部且会变**：DSH 的 RPC 端点、事件通道、认证方式、模型 id 都在演进，
  每次适配都要回答「新旧版本怎么共存」「失配怎么告知」。
- **平台矩阵宽**：三操作系统 × 本地/三种远程 × 新旧 dsh，方案写不清就会漏场景。
- **历史事故都有「没写下来的决策」**：如「为什么不关掉 dsh 的认证而是做代理」「为什么去重签名只取最后一条消息」。
  spec + plan 是这些决策的归档处。

## 2. 目录与命名

```
docs/sdd/
├── README.md                    本文件
├── templates/
│   ├── spec.md                  规格模板（做什么/为什么/验收）
│   ├── plan.md                  方案模板（怎么做/影响面/回退）
│   └── tasks.md                 任务模板（分步/红绿顺序）
└── specs/
    └── NNN-kebab-case/
        ├── spec.md
        ├── plan.md
        └── tasks.md
```

- 编号：三位数字，全局递增，不复用（`001`、`002`…）。
- 名称：小写 kebab-case，2-5 个词，描述**能力**而不是实现（`workspace-file-links`，不是 `add-postmessage`）。
- 一个规格只解决**一个用户可感知的能力或一个明确的缺陷类**。缺陷也用 spec（标题写清故障现象）。
- 已实现规格保留在仓库（不要删），作为行为基线与回归依据；被取代时状态改 `superseded` 并注明被谁取代。

状态机：

```
draft ──► approved ──► implementing ──► implemented ──► superseded
  │           │
  └───────────┴──► rejected（记录为何不做）
```

`spec.md` 顶部必须写 `状态`、`编号`、`负责人`、`关联提交/PR`。

## 3. 七个阶段与门禁

| # | 阶段 | 产物 | 完成标准（门禁） |
| --- | --- | --- | --- |
| 0 | 立项 | Issue / 问题描述 | 能一句话说清「谁的什么场景现在不行」；不是「换个写法」类纯内部改动 |
| 1 | Spec | `spec.md` | 目标/非目标清晰；验收标准全部是可执行 Given/When/Then；兼容矩阵填完；引用相关宪法条款 |
| 2 | Clarify | spec 更新 | 歧义清零：边界条件（空/超长/越界/并发/超时）、失败提示文案、配置开关语义都已确定 |
| 3 | Plan | `plan.md` | 影响文件列全；契约变更标注新旧兼容；安全审查逐项过；回退方案可执行 |
| 4 | Tasks | `tasks.md` | 任务 ≤ 半天粒度；每个行为任务都有前置 `[test]`；依赖与并行标注清楚 |
| 5 | Implement（TDD） | 代码 + 测试 | 每个 `[test]` 先红、每个 `[impl]` 变绿；`npm test` 全绿；任务勾选 |
| 6 | Verify | spec「验证记录」 | 单测/ e2e / 实机（F5、特定平台、Remote）结论写回；已知限制更新 |
| 7 | Release | 版本 + CHANGELOG + README + tag | 三处版本一致；Release 工作流绿；见 [../CI-CD.md](../CI-CD.md) |

### 轻量例外（不写 spec，但仍需测试与说明）

- 纯文档 / 注释 / 错别字；
- 无行为变化的内部重构（须说明「行为不变」的依据：现有测试全绿）；
- 依赖版本探测或只读诊断信息调整。

判断标准：**用户可观察行为是否变化**。变化了就必须有 spec；修 bug 也算（现象即问题陈述）。

## 4. Spec 写什么（要点）

1. **用户故事**：`作为 <角色>，我希望 <能力>，以便 <收益>`。角色只有三类：VS Code 用户、
   DSH 二次开发者、维护者。
2. **验收标准**：一条一个 Given/When/Then，且必须能映射到某个测试断言。
   例：`Given dshPanel.workspaceFileLinkAction=off，When 点击对话里的 src/a.ts，Then 不安装插件且不发送 ack，DSH 侧边栏照旧打开`。
3. **非目标**：明确不做什么（例如「不接管 DSH 侧边栏内部链接」），防止范围蔓延。
4. **兼容矩阵**：行 = 场景（Win/macOS/Linux × 本地/WSL/SSH/容器 × 新版/旧版 dsh），
   列 = 期望行为/回退行为，空格填「不适用」也要写。
5. **约束**：引用宪法条款号，并把相关红线具体化（如「令牌不得进日志」）。
6. **失败与提示**：每个失败分支的**用户可见文案与出口动作**（宪法第三条）。

## 5. Plan 写什么（要点）

- **影响面**：文件/函数表 + 「是否触碰安全数据流」列。
- **契约变更**：DSH RPC/事件、VS Code API、webview 消息协议、插件协议、配置项。逐项写「新→旧回退」。
- **状态与并发**：新增全局状态谁置位/谁清理；并发去重方式（单飞 Promise / Map）。
- **回退方案**：功能开关（配置项）、代码级回退（保留旧路径）、发布级回退（补丁版本）。
- **测试策略**：按 L1-L4 分层列出要加的断言（见 [../TESTING.md](../TESTING.md)），标出哪些必须 e2e。
- **开放问题**：实现中可能推翻方案的假设，写清「若 X 则改为 Y」。

## 6. Tasks 写什么（要点）

- 顺序固定：`[test]` → `[impl]` →（可选）`[docs]`；基础设施（导出 `__internals`、桩扩展）排最前。
- 每个任务写「完成判据」，而不是「做什么动作」。
- 标 `[P]` 表示可并行（不同文件/无依赖）。
- 阶段划分建议：0 准备 → 1 纯逻辑 → 2 宿主接入 → 3 插件/页面侧 → 4 文档与发布。

## 7. 实现中要改 spec 怎么办

1. 先改 `spec.md`（验收标准/非目标/兼容矩阵），在「变更历史」记一行：日期 + 原因 + 影响。
2. 若结论反转（原方案不可行），把被否方案写进 `plan.md` 的「被否方案与原因」，不要删。
3. 任务随之调整；**代码不得领先于 spec 合入**（同 PR 内改完即可）。

## 8. 评审检查清单（PR 用）

- [ ] 关联 spec 且状态已推进（`approved` → `implementing` → `implemented`）
- [ ] 每条验收标准都能指到一条断言/测试
- [ ] 负面用例（开关关闭、平台不符、非法输入、超时）已覆盖
- [ ] 契约变更保留了新旧回退路径
- [ ] 安全数据流（子进程/webview/路径/token）无放宽，或已评审
- [ ] 用户可见失败都有提示与出口
- [ ] README / CHANGELOG / 版本号同步（若发布）
- [ ] `npm test` 全绿；必要时的 e2e/实机结论已写入 spec
