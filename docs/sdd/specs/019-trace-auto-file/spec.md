## 1. 背景与问题

018 落盘后暴露了一个信息缺口：文件里只有「扩展侧」事件（开关、手动显隐、策略变更…），
而复盘「拉宽后侧栏又被藏回去」必需的 `layout`（轨道/折叠/抽屉/ratio/rect）、`resize`、
`recompute`（auto 是否介入）都在**面板侧中继的内存环形缓冲**里，只有执行
「DeepSeek Harness: 导出 DSH 侧栏诊断」才会一起落盘。用户实测日志里只有 9 条 `[sidebar-state]`，
看不到任何布局现场，必须手动导出才有数据。

要求：把「导出诊断」里的必要信息**自动写进日志**，但**不要影响性能——尤其关闭落盘时不影响性能**。

## 2. 目标

- 开启 `dshPanel.debugLogToFile` 后，面板侧事件流自动批量写入日志文件，**无需再手动导出**：
  `layout / recompute / hidden / resize / toggle / config / ratio-fallback` 与 `[env]`（缩放/字号）。
- 关闭时：面板不建队列、不起定时器、不发任何消息；每个事件只多**一次布尔判断**。
- 批量：默认 **1 秒一包**、单包 ≤200 条；扩展侧**一包一次追加**（不逐条写）。
- 热切换：改设置立即生效（开启后马上开始推送；关闭后清空未发送增量）。
- 安全：事件条目与诊断包共用同一套白名单净化（`t/ev/v` 形状 + 控制字符清洗 + 长度截断）。

## 3. 非目标

- 不推送页面侧插件的 `trace`（其信息已由中继的 `layout` 条目覆盖；需要完整页面日志时仍可手动导出）。
- 不做持久化队列/重放：面板销毁即丢未发送增量。
- 不改变输出面板与导出命令的行为（仍然可用）。

## 4. 用户故事

- 作为 **VS Code 用户**，我打开落盘后，出问题时不用再记得「导出诊断」，日志里就有现场。
- 作为 **维护者**，我希望拿到日志就能复盘（布局/覆盖/auto 三者顺序一目了然），且用户不开这个开关时零负担。

## 5. 验收标准（必须可执行）

- **AC-1（关闭零成本）**：Given `debugLogToFile` 未开启，When 面板产生布局/resize 等事件，Then 不发送任何
  `dsh-sidebar-trace` 消息（不建队列、不起定时器）；扩展侧收到该消息也立即返回。
- **AC-2（开启自动落盘）**：Given 开启，When 产生事件，Then 在 1 秒内收到 `dsh-sidebar-trace`（含 `layout`），
  扩展把它写进日志文件（`[sidebar-trace]`，每行带 `HH:MM:SS.mmm`），**不需要手动导出**。
- **AC-3（批量与上限）**：Given 短时间大量事件，When 未到 1 秒，Then 单包 ≤200 条；满 200 立即发送。
- **AC-4（热切换）**：When 设置从关→开，Then 后续事件开始推送；从开→关，Then 清空未发送增量、不再推送。
- **AC-5（净化）**：Given 事件含非法 `t`/`ev` 或控制字符，Then 非法条目丢弃、`v` 清洗截断（与诊断包一致）。
- **AC-6（环境行）**：Given 开启设置，Then 日志写入 `[env]`（`window.zoomLevel` / `editor.fontSize` / `fontScale`）。

## 6. 兼容矩阵

| 场景 | 行为 | 说明 |
| --- | --- | --- |
| 落盘关闭（默认） | 事件流完全不产生 | 与 018 一致 |
| 落盘开启 | 1s 批量推送 + 单次追加 | 面板重载后由构建参数重新注入 |
| 面板未打开 → 再打开 | 重新按当前设置注入 | 不需要重启 dsh web |
| 旧插件/旧 dsh | 事件流仍工作（中继侧实现） | 与插件版本无关 |

## 7. 约束（引用宪法）

- 第三条：开启/失败通过 018 的既有提示；事件流失败静默丢弃（面板销毁时无处可写，属预期）。
- 第五条：条目净化复用 `normalizeDiagEntries`；不新增字段与权限。
- 第六条：AC-1..AC-6 全部离线可测（`vm` 中继 + 宿主桩）。

## 8. 失败与提示

| 失败场景 | 行为 | 出口 |
| --- | --- | --- |
| 面板已销毁时推送 | 静默丢弃（无接收方） | 重新打开面板即恢复 |
| 日志目录不可写 | 沿用 018 的状态栏一次性提示 | 修权限/关闭开关 |
| 事件条数异常多 | 满 200 立即发 + 1s 定时；文件 2MB 轮转 | 018 的轮转策略 |

## 9. 风险与开放问题

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 持续拖动时日志增长快 | 导致轮转过频、早期现场被挤出 | 2MB 轮转保留最近约 2 万行；必要时可再降频（当前 1s/200 条） |
| 同步追加 20KB/包 | 极端情况下 ~0.5ms/包 | 实测 200 条/包 ≈0.47ms，且 ≤1 包/秒 |
